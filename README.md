# 房贷测算台

一个纯前端的房贷测算工具：等额本息 / 等额本金逐月拆解、公积金与商贷组合贷、
任意年份提前结清的总支出与省息测算。零构建、零第三方运行时依赖。

## 快速开始

```bash
node tools/serve.mjs          # 打开 http://127.0.0.1:8080
```

页面使用 ES Modules，**不能用 `file://` 直接双击打开**（浏览器会以 CORS 为由拒绝加载模块），
必须经由本地 HTTP 服务。`tools/serve.mjs` 只依赖 Node 内置模块，无需 `npm install`。

| --- | --- |

| 公积金额度 | 按城市政策校验上限（青岛/北京/上海/广州/深圳/杭州），多子女、绿色建筑等上浮可叠加，超限提示并可一键裁剪 |

## 计算规则

金额在内部一律用**整数分**流转，每期四舍五入到分，末期以剩余本金兜底。
这样 360 期跑下来本金合计精确等于贷款额，不会出现"还完了还差 0.01 元"的浮点残差。

### 等额本息

```
月供 M = P · i · (1+i)^n / ((1+i)^n − 1)
当期利息 = 上期末剩余本金 · i
当期本金 = M − 当期利息
```

i 为月利率，取 `年利率 / 12`（名义利率按月计息），与国内房贷合同一致，
而不是 `(1+r)^(1/12) − 1` 那种有效年利率换算。

### 等额本金

```
当期本金 = P / n（四舍五入到分）
当期利息 = 上期末剩余本金 · i
月供 = 当期本金 + 当期利息
```

### 提前结清

严格区分两个金额，这是最容易混淆的地方：

- **结清当天要支付** = 剩余本金 + 违约金（当天实际转账金额）
- **全周期总支出** = 已付月供 + 结清当天要支付（这件事从头到尾的总成本）

由此可得两条恒等式，`tests/core.test.mjs` 对每个采样点逐一校验：

```
全周期总支出 = 本金 + 已付利息 + 违约金
省下利息     = 原计划总利息 − 已付利息 − 违约金
```

因为两条路径偿还的本金完全相同，差额只可能来自利息与违约金。

违约金按剩余本金乘以比例计收，并支持设置免罚期（还款满 X 期后不再收取）。

### 部分提前还款

与一次性结清不同，这里还款后合同继续，必须**以结清点为新起点重建摊销表**。
两种策略：

- **缩短年限**：月供不变，期数减少（总利息更省）
- **减少月供**：期数不变，月供降低（月供压力更小）

缩期时的期数是反解出来的（年金公式变形）：
`n = -ln(1 − P·i / M) / ln(1+i)`，其中 P 是还款后剩余本金、M 是原月供。
当 `P·i ≥ M` 时月供不足以覆盖利息，永不结清，抛错而不是返回 Infinity。

两处容易做错的地方：

1. **缩期时月供必须保持恒定**。若让年金公式按新期数重算，月供会变，
   违背「缩期」的约定。`buildSchedule` 的 `fixedMonthly` 参数就是为此存在。
2. **等额本金的缩期不是「把剩余本金摊到更少期数」**——那会让每期本金变小，
   等于降月供。正确做法是保持「每期还款本金」不变，提前还掉一部分后
   期数自然缩短。

恒等式同样成立：`全周期总支出 = 各期月供 + 提前还款 + 违约金 = 本金 + 已付利息 + 违约金`。
注意「总支出」必须包含提前还款那笔钱，否则恒等式不闭合。

组合贷暂不支持部分提前还款测算（两笔的利率与还款方式不同，作用于哪笔
会显著影响结果），界面会明确提示。

### 公积金贷款额度

各地上限差异极大，且 2026 年普遍上调过。以青岛为例（2026-04-20 新政）：
双缴存 130 万 / 单缴存 90 万，多子女 +30%、现房 +10%、绿色建筑 +30%、
高层次人才 +30%、灵活就业满 2 年 +10%，各项可叠加，叠加上浮后封顶 240/160 万。

**计算顺序不可颠倒**：

```
1. 先按四项约束算出可贷额度（此处只校验最高额度）
2. 再按命中情形的上浮比例放大
3. 最后用封顶值截断
```

若直接在上限上加比例，会算出高于官方封顶的数字。单测用官方问答里的
「多子女双缴存 169 万 / 单缴存 117 万」直接验证这条顺序。

额度取整规则：以 1 万元为起点，按 5000 元整数倍确定。

超限处理是**提示不阻断**——这是测算工具，用户有权模拟超出实际上限的方案，
但必须知道自己超了多少，并可以一键裁剪到上限。

**边界**：真实可贷额度还要按账户余额倍数（青岛 20 倍，新市民/青年人 25 倍）
与还贷能力（月缴存基数 × 40% × 12 × 年限）等四项取最低值，那依赖个人缴存明细，
各地公式也不统一。本工具只做上限校验，并在界面上明确说明这一点。

### 利率分段：LPR 逐年重定价

真实房贷的合同结构是 **执行利率 = 重定价日 LPR + 加点**：
加点在整个合同期固定不变，LPR 每 12 期重新取值。

启用后，等额本息在**每个重定价周期起点**按「当时的剩余本金 + 剩余期数 + 新利率」重算月供。
这里有两个容易做错的地方：

1. 不能把新利率套进**原始本金与原始期限**去算——那会得到错误的月供。
2. 不能每期都重算——即使利率没变，逐期四舍五入的累积也会让月供出现
   `4490.44 / 4490.45` 两个值，违背「月供恒定」这条合同约定。因此只在利率
   真正变化时才重算。

等额本金不受影响：每期本金固定，只是按当期利率计息。

LPR 走势是假设，不是预测。快捷情景只作用于前 10 年（更贴近实际预测窗口），
需要更长的假设可逐年手填。快捷情景按 30 年线性外推会把 LPR 减成负数，
看似精确实则荒谬，所以刻意不做。

## 外观主题

三套主题可在右上角切换，偏好写入 localStorage：

| 主题 | 视觉语言 |
| --- | --- |
| **深色**（默认） | Apple HIG — 纯黑背景、半透明标签、毛玻璃、铜色强调 |
| **浅色** | Apple HIG — 系统灰背景、白卡片、铜色强调 |
| **小米** | HyperOS — 明亮通透、品牌橙 `#FF6900`、更大圆角、渐变点缀、带色温的阴影 |

Apple 那两套强调色保留铜色（产品的识别色）但质感对齐系统强调色；
小米那套则是完整的品牌橙体系，圆角整体大一档，强调元素走渐变。

**小米主题还带布局变体**（不只换肤）：KPI 变成横向滑动的大卡片
（`scroll-snap`，固定 264px 宽，第 4 张自然溢出以暗示可滑动），
输入面板拆成独立卡片流（贷款构成 / 金额 / 期限 / 高级设置各自成卡）。
Apple 两套仍是标准双栏 + 四列 KPI 网格，结构不受影响。

主题由 CSS 变量驱动，图表的渐变 `stop-color` 同样走变量，切换时无需重绘。

几个刻意的取舍：

- **材质优先于边框**：层次靠背景色差与毛玻璃建立，分隔线用 0.5px 半透明灰
- **渐变不牺牲语义**：小米主题下 KPI 顶部色条虽是渐变，但仍按
  「总额/月供/利息/总支出」各自取色，不抹掉信息层次
- **累计值图表纵轴从 0 起**：截断会夸大差距；月供这类窄范围才放缩纵轴，
  且月供变化不足 2% 时也退回 0 起点，避免把噪声画成「变化」
- **渐变填充**：柱状与面积图用垂直渐变，`stop-color` 由 CSS 变量控制，
  `fill` 由 attribute 指向渐变——两者不能都走 CSS，否则会被覆盖

```js
document.documentElement.dataset.theme  // 'dark' | 'light'
localStorage.getItem('loanlab-theme')   // 用户手动选择后记住
```

配色集中在 `styles/tokens.css`，改主题只动这一个文件。

## Web 规范合规

用 Google Chrome 团队的 [Modern Web Guidance](https://github.com/GoogleChrome/modern-web-guidance-src)
做静态扫描与规范对照：

```bash
npx -y modern-web-guidance@latest legacy-scan .
npx -y modern-web-guidance@latest retrieve dark-mode
```

当前 `legacy-scan` 结果：**0 findings**。

关键合规点：

- **配色方案**：`<meta name="color-scheme">` 与 `:root { color-scheme: light dark }`
  配合，并用 `:has()` 把 meta 映射回 CSS 属性（meta 只是提示，CSS 声明会覆盖它）。
  小米主题本质是浅色方案，映射为 `light`
- **滚动条**：只用标准 `scrollbar-width` / `scrollbar-color`。
  算出的 `scrollbar-width` 非 `auto` 会让 `::-webkit-scrollbar` 失效，两套不能叠加
- **表格语义**：`<th scope="col">` + `<caption>`（视觉隐藏，供屏幕阅读器）
- **live region 克制**：结果区刻意**不**设 `aria-live`——输入时每帧都在变，
  整区播报等于噪声。错误与超限警告用 `role="alert"` 单独播报
- **JS 现代化**：用 `toReversed()` 替代「浅拷贝后 reverse」，
  用 `replaceChildren()` 替代 `innerHTML = ''`

## 已知边界

这些是刻意的取舍，不是遗漏：

- **重定价日按「每 12 期」对齐**：实际合同有「每年 1 月 1 日」和「放款日对月对日」两种，
  放款不在 1 月时两者会错开几个月。本工具按对月对日处理。
- **LPR 走势是假设，不是预测**：未来 LPR 无法预知，工具只负责把假设算对。
  需要评估「LPR 涨到多少会怎样」这类问题时，用逐年编辑器填入压力情景即可。
- **公积金不走 LPR**：公积金按国家统一利率，通常也是次年 1 月 1 日统一调整，
  本工具按固定利率处理，可直接填最新值。
- **不含税费**：契税、评估费、保险费、提前还款手续费等不计入。
- **违约金为简化模型**：按剩余本金乘比例，支持免罚期；不模拟"收取 X 个月利息"等按银行差异巨大的规则。
- **部分提前还款未实现**：目前只支持一次性结清。若要支持"还一部分后缩短年限或降低月供"，
  需要以结清点为新起点重建摊销表，`core/` 已按可重入的方式组织，扩展时不必改动现有函数。
- **组合贷期限共享**：两笔共用同一期限，符合银行对组合贷的要求；`mergeSchedules` 本身支持
  期限不一致的表合并，只是界面暂未暴露该入口。
